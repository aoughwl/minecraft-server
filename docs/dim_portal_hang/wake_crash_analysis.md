# int_wake.exe crash: root cause (Nov 19)

Verdict: PROVEN, a stale/inconsistent nimcache build, not a race and not the jobpool change.

* ARC is atomic in this toolchain: `=dup` is `lock addq $1,(rcx)`, `=destroy` is `lock subq` (toolchain/aowlmony/root/lib/std/system/arcops.nim, `arcInc/arcDec` use `__atomic_*` SEQ_CST; no mm switch exists or is set in buildint.sh). So hypothesis (b), non-atomic refcounts corrupted by two dim workers, is refuted for ref counts.
* gdb on int_wake.exe (reproduced, port 26210, one bot): fault at `lock addq $1,(%rcx)` with rcx = 0xfffffffb0000000d, not nil. In runTickData, `w` = `BlockWorld(world.blockWorld)` = 0x2000c164000, which holds plain table data (0xfffffff8.../0xfffffffb... counters with sequence numbers 3,4,5...), so `w.blockRegistry` (w+0x3c0) is garbage.
* Why: the World object layouts disagree between modules of the same exe. `runTickData`/`tickBlockEntities` (worldadapter, module worm5ecfw1) read World.blockWorld at +0x408; `loadWorld` (worldmod, worsj29i7) stores it at +0x428; `updateActiveChunks` writes a different field (HashSet `activeChunkSet`) at +0x408, which is exactly what the reader sees as blockWorld. +0x20 = the 32 byte `activeChunkSet` field added in 2e8604d (Nov 18 23:33). int_all.exe (built 21:58, before that commit) is consistent: both sides use +0x408. int_wake.exe was incrementally rebuilt: worldmod was recompiled with the new World, worldadapter was not. Watchpoint on world+0x408 confirms the first write is `updateActiveChunks` on the dim worker.
* So it crashes on the first dim job only because only that path (and any tick) touches blockWorld via worldadapter; it is deterministic (17/17), independent of the broadcast change. Likely every module that reads a World field after +0x3e0 and was not rebuilt is wrong; the main-thread (non-dim) path would fail too, probably, but ungated runs were not tried; unknown.
* int_all.exe is NOT lucky about this: its layout is consistent. Whether the dim gate has other races (unsynchronised Tables, shared non-ref state) is a separate question this analysis does not answer; no evidence from this crash that earlier gated passes were unsafe on ref counts.
* Not verified: int_clean.exe (clean cache) should show LAYOUT-OK and no crash; the lost-wakeup fix remains unverified until then.
* Fix: rebuild with a fresh --nimcache (in progress). Tripwire so this cannot recur silently: docs/patches/world-layout-tripwire.patch (adds tools/check_world_layout.sh, `git apply -p1`; gdb on the exe; symbol hashes may need updating after a clean build). No src change is needed, no atomic-ARC switch (already atomic).
* Also: the nimcache dependency tracking did not invalidate worldadapter when an imported type changed layout. That is a toolchain bug worth reporting (X1 hsl crash was the same class).
